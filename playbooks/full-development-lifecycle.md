# 完整开发闭环

```text
准备 → 理解 → 接手 → 方案 → 实施 → 验证 → 审查 → 交付 → 沉淀
```

## 阶段与检查点

1. **准备**：区分咨询、分析、Review、修改与交付；确认当前用户要求和授权范围。
2. **理解**：用 `templates/requirement-card.md` 记录中大型任务或用户要求保存的需求；小任务在对话内明确验收即可。只澄清会改变实现、风险或验收的未知项。符合 `core/task-routing.md` 触发条件时，按需启动内置需求压力测试：代理先查事实，再逐个确认关键决策并给出推荐默认方案；小而明确的任务默认跳过，但用户明确要求深入把关时，小而明确的任务也进入压力测试；不穷尽无关分支。
3. **接手**：按需调用 `project-onboarding`，读取项目规则、Git 工作区、真实入口和命令；选择匹配 Profile 与项目卡，不覆盖已有改动。
4. **方案**：Small 直接处理；Medium 明确影响范围和任务清单；Large 使用 `templates/change-design.md` 与 `templates/task-plan.md`，必要时等待用户确认关键设计。项目已有 OpenSpec 等格式时沿用，不另造一套。
5. **实施**：按 `debugging` 与 `playbooks/fix-bug.md` 处理故障，或按本流程处理功能。先有复现/测试，再做聚焦修改；一次只推进一个任务，不扩大到无关重构。
6. **验证**：使用 `targeted-verification` 和实际项目命令；逐项核对完成标准，并把真实命令与结果记入 `templates/verification-report.md`。
7. **审查**：使用 `code-review` / `playbooks/review-change.md` 检查差异、安全、兼容性和文档同步；审查发现未处理前不能称完成。
8. **交付**：使用 `git-delivery`；汇报变更、测试、当前分支和未提交状态。未经用户明确确认，不执行 `git push`。
9. **沉淀**：只有重复、稳定、有证据且可脱敏的经验才交给 `extract-project-knowledge`，先入候选区。

## 任务规模

| 规模 | 判断 | 产物 |
| --- | --- | --- |
| Small | 咨询、只读，或单点且低风险改动，不触及共享契约、数据、权限或外部系统 | 简化理解、定向验证；不自动创建文件 |
| Medium | 一个业务流程/子系统内多文件，验收基本明确 | 需求卡、短方案/任务清单、实施和审查 |
| Large | 跨模块/平台、公共接口、迁移、安全/权限、资金、生产或外部写入；关键需求未知也升级 | 完整需求卡、设计、任务、阶段验证、审查；按需交接 |

风险可以提高流程等级；仅仅文件较多不会自动升级。未影响方案的次要细节允许明确假设继续。

## 文件与暂停规则

- 只有用户要求保存、项目规则要求留档或任务跨会话时才创建持久化产物；创建前说明目标仓库内的准确路径。
- 暂停且确需恢复时按 `templates/session-handoff.md` 记录阶段、分支、未提交修改、验证结果和下一步。不得把未提交修改误报为已保存。
- 阶段阻塞时说明证据、风险和所需决定，不跳过检查点或伪造验证结果。
